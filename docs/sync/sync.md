# Синхронизация — Change Events

Система синхронизации позволяет клиенту узнать, что изменилось с момента последней сессии, и получить актуальное состояние без полной перегрузки данных. Она состоит из трёх частей: журнала изменений в базе данных, gRPC-запроса для опроса и gRPC-стрима для мгновенного уведомления.

## Журнал изменений

Каждая мутация над доменными объектами записывается в таблицу `change_events`. Запись появляется после успешного сохранения — при создании, обновлении и удалении сущности. Сейчас отслеживаются операции над `breath_session`.

| Колонка | Тип | Описание |
|---------|-----|----------|
| `id` | `SERIAL` | Монотонно возрастающий курсор |
| `entity` | `varchar` | Тип сущности, например `breath_session` |
| `refId` | `uuid` | ID изменившейся записи |
| `action` | `varchar` | `created`, `updated` или `deleted` |
| `userId` | `uuid` | Пользователь, которому предназначено событие |
| `createdAt` | `timestamp` | Время записи |

Индекс `(userId, id)` обеспечивает эффективную выборку событий конкретного пользователя с пагинацией по курсору.

## gRPC — unary-запрос GetChanges

RPC определён в `proto/sync.proto` как `rpc GetChanges(GetChangesRequest) returns (GetChangesResponse)` и обрабатывается `SyncGrpcController` (SyncModule). Идентификатор пользователя извлекается из метаданных gRPC через `GrpcAuthInterceptor` — в тело запроса не передаётся.

**Поля запроса `GetChangesRequest`:**

| Поле | Тип | Описание |
|------|-----|----------|
| `after` | `int64` | Вернуть события с `id > after`. При первой синхронизации передавать `0`. |
| `limit` | `int32` | Максимум событий в ответе (от 1 до 100, по умолчанию 100). |

**Ответ `GetChangesResponse` — нормальный случай:**

```proto
result: {
  payload: {
    events: [
      { id: 42, entity: "breath_session", ref_id: "uuid...", action: "created", created_at: "..." },
      { id: 43, entity: "breath_session", ref_id: "uuid...", action: "updated", created_at: "..." }
    ],
    cursor: 43,
    has_more: false
  }
}
```

Поле `cursor` нужно сохранить и передать как `after` в следующем запросе. Если `has_more: true` — повторить запрос с тем же курсором до получения `has_more: false`.

**Ответ — сигнал полной пересинхронизации:**

```proto
result: { full_resync: true }
```

Возвращается, когда переданный `after` меньше минимального сохранённого события в журнале — то есть клиент отстал настолько, что часть истории уже удалена. Клиент должен удалить локальный кэш и загрузить данные заново с нуля.

## gRPC — серверный стрим WatchChanges

RPC определён в `proto/sync.proto` как `rpc WatchChanges(WatchChangesRequest) returns (stream ChangeEvent)` и обрабатывается `SyncStreamGrpcController` (RealtimeModule).

**Поля запроса `WatchChangesRequest`:**

| Поле | Тип | Описание |
|------|-----|----------|
| `after_id` | `int64` (опционально) | Если передан — сначала отправляется догоняющий батч событий с `id > after_id`, затем продолжается живой стрим. Если не передан — стрим начинается с момента подключения. |

Если курсор старше самого раннего сохранённого события, стрим завершается со статусом `FAILED_PRECONDITION` — клиент должен сделать полную пересинхронизацию через `GetChanges`.

События батчатся с задержкой 300 мс `SyncStreamService` перед отправкой в стрим. Каждый `ChangeEvent` содержит список объектов `SyncEventDto` — той же формы, что и события в `GetChanges`:

```proto
ChangeEvent {
  events: [
    { id: 42, entity: "breath_session", ref_id: "uuid...", action: "created" }
  ]
}
```

Стрим доставляет полные данные событий напрямую — клиенту не нужно делать дополнительный запрос `GetChanges` после получения push-уведомления.

## TTL и очистка

События хранятся 30 дней. Очистка запускается ежедневно в полночь через `SyncService.purgeOldEvents`. Именно поэтому возможен сценарий `full_resync`: если клиент не синхронизировался дольше периода хранения, часть событий уже удалена.

Срок хранения настраивается через аргумент `purge(olderThanDays)` — сейчас захардкожен в 30 дней.

## Добавление новых сущностей в журнал

Чтобы отслеживать изменения новой сущности, нужно после каждой мутации вызвать `ChangeLogService.log(entity, refId, action, userId)` и выбросить событие `CHANGE_EVENT_LOGGED` через `EventEmitter2`. `SyncStreamService` подхватит его автоматически и разошлёт по всем активным gRPC-стримам пользователя.
