# Синхронизация — Change Events

[Back to README](../../README.md)

Система синхронизации позволяет клиенту узнать, что изменилось с момента последней сессии, и получить актуальное состояние без полной перегрузки данных. Она состоит из трёх частей: журнала изменений в базе данных, REST-эндпоинта для опроса и WebSocket-push для мгновенного уведомления.

## Журнал изменений

Каждая мутация над доменными объектами записывается в таблицу `change_events`. Запись появляется после успешного сохранения — при создании, обновлении и удалении сущности. Сейчас отслеживаются операции над `breath_session`.

| Колонка | Тип | Описание |
|---------|-----|----------|
| `id` | `SERIAL` | Монотонно возрастающий курсор |
| `entity` | `varchar` | Тип сущности, например `breath_session` |
| `refId` | `uuid` | ID изменившейся записи |
| `action` | `varchar` | `created`, `updated` или `deleted` |
| `userId` | `uuid` | Пользователь, которому предназначено событие |
| `createdAt` | `timestamp` | Время записи |

Индекс `(userId, id)` обеспечивает эффективную выборку событий конкретного пользователя с пагинацией по курсору.

## REST — GET /sync/changes

Эндпоинт требует JWT-аутентификации.

**Параметры запроса:**

| Параметр | Тип | Описание |
|----------|-----|----------|
| `after` | `number` | Вернуть события с `id > after`. При первой синхронизации передавать `0`. |
| `limit` | `number` | Максимум событий в ответе (от 1 до 100, по умолчанию 100). |

**Ответ — нормальный случай:**

```json
{
  "events": [
    { "id": 42, "entity": "breath_session", "refId": "uuid...", "action": "created", "createdAt": "..." },
    { "id": 43, "entity": "breath_session", "refId": "uuid...", "action": "updated", "createdAt": "..." }
  ],
  "cursor": 43,
  "hasMore": false
}
```

Поле `cursor` нужно сохранить и передать как `after` в следующем запросе. Если `hasMore: true` — повторить запрос с тем же курсором до получения `hasMore: false`.

**Ответ — сигнал полной пересинхронизации:**

```json
{ "fullResync": true }
```

Возвращается, когда переданный `after` меньше минимального сохранённого события в журнале — то есть клиент отстал настолько, что часть истории уже удалена. Клиент должен удалить локальный кэш и загрузить данные заново с нуля.

## WebSocket — событие sync:changed

Когда пользователь подключён к `module_session` и в журнале появляется новое событие, `SyncNotifierService` push-уведомляет клиента без необходимости опрашивать REST. Уведомления батчатся с задержкой 300 мс — несколько изменений, произошедших подряд, объединяются в одно сообщение.

**Формат события:**

```json
{
  "events": [
    { "id": 42, "entity": "breath_session", "refId": "uuid...", "action": "created" }
  ]
}
```

Получив `sync:changed`, клиент должен запросить `GET /sync/changes?after=<последний_известный_cursor>`, чтобы получить полные данные событий с временными метками.

## TTL и очистка

События хранятся 30 дней. Очистка запускается ежедневно в полночь через `SyncService.purgeOldEvents`. Именно поэтому возможен сценарий `fullResync`: если клиент не синхронизировался дольше периода хранения, часть событий уже удалена.

Срок хранения настраивается через аргумент `purge(olderThanDays)` — сейчас захардкожен в 30 дней.

## Добавление новых сущностей в журнал

Чтобы отслеживать изменения новой сущности, нужно после каждой мутации вызвать `ChangeLogService.log(entity, refId, action, userId)` и выбросить событие `CHANGE_EVENT_LOGGED` через `EventEmitter2`. `SyncNotifierService` подхватит его автоматически, если пользователь онлайн.
