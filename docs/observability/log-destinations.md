# Логирование — назначение вывода

`LOG_DESTINATION` определяет, куда сервер отправляет логи. По умолчанию вывод идёт только в файлы — поведение, идентичное тому, что было до введения этой переменной.

## Режимы

`LOG_DESTINATION=file` (по умолчанию) — логи пишутся в консоль и файлы с ротацией (`logs/error-*.log`, `logs/combined-*.log`). OTLP-трафик отсутствует, SDK не инициализируется.

`LOG_DESTINATION=grafana` — файловый вывод отключён, логи уходят только в OTLP-эндпоинт (Loki). При старте сервиса автоматически отправляется маркер `service.start`, по которому можно отличить перезапуск от паузы в потоке.

`LOG_DESTINATION=both` — активны оба канала одновременно: файлы и OTLP. Маркер `service.start` отправляется так же, как в режиме `grafana`.

Любое нераспознанное значение (например, опечатка) трактуется как `file` — сервис не теряет логи.

## Переменные окружения

| Переменная | По умолчанию | Описание |
|------------|-------------|----------|
| `LOG_DESTINATION` | `file` | Назначение вывода логов: `file`, `grafana` или `both`. |
| `OTLP_ENDPOINT` | `http://localhost:3100/otlp/v1/logs` | URL OTLP-эндпоинта (используется только в режимах `grafana` и `both`). |

## Требование к реальному окружению

Обе переменные читаются в `main.ts` до того, как `ConfigModule` разбирает `.env`. Это означает, что их нельзя задать через `.env`-файл проекта — они должны быть выставлены в окружении процесса: через shell, Docker `env_file` или `environment` в `docker-compose`. Это то же самое ограничение, что действует для `LOG_LEVEL` и `NODE_ENV`.

В продакшне значения подставляются через `env_file: .env.prod` в `docker-compose.prod.yml`.
