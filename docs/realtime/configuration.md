# Realtime — Конфигурация

Все параметры realtime-системы задаются через переменные окружения. Значения по умолчанию рассчитаны на типичные условия мобильного использования.

| Переменная | По умолчанию | Описание |
|------------|-------------|----------|
| `WS_RECONNECT_GRACE_MS` | `30000` | Время ожидания переподключения в мс. Если пользователь не восстановил стрим за этот период, сессия помечается как `abandoned`. Применяется независимо к корневой сессии и к каждой дочерней. 30 секунд покрывают переключение LTE→WiFi, фоновую оптимизацию ОС и кратковременную потерю сигнала. |
| `WS_EMPTY_ROOT_TTL_MS` | `600000` | Время жизни «пустой» корневой сессии в мс (10 мин). Janitor уничтожает корень, у которого нет ни одной активной дочерней сессии, по истечении этого значения. Одно лишь наличие биоданных корень не защищает. |
| `WS_SESSION_MAX_IDLE_MS` | `600000` | Порог простоя сессии в мс (10 мин). Watchdog завершает сессии со статусом `active` или `disconnected`, у которых `lastActivityAt` старее этого значения. Исключение: сессия с живым подписчиком потока не уничтожается — см. раздел ниже. |
| `WS_SESSION_SWEEP_INTERVAL_MS` | `60000` | Интервал между запусками watchdog-свипа в мс (1 мин). При каждом запуске сервис проверяет все незавершённые сессии и уничтожает простоявшие дольше `WS_SESSION_MAX_IDLE_MS`. |
| `WS_MIN_SESSION_DURATION_S` | `10` | Минимальная длительность сессии в секундах для учёта в статистике. Сессии короче не добавляются в `user_stats` — защита от случайных нажатий. |
| `WS_STREAM_MAX_BUFFER_BYTES` | `204800` | Максимальный размер кольцевого буфера инструкций на одну сессию в байтах (200 КБ). При достижении лимита новые сэмплы вытесняют старые; счётчик вытесненных отражается в `dropped_count`. |
| `WS_STREAM_MAX_SESSIONS` | `1000` | Максимальное количество сессий с активными буферами одновременно. Защита от исчерпания памяти при пиковой нагрузке. |
| `WS_TELEMETRY_MAX_PAYLOAD_BYTES` | `65536` | Максимальный размер одного сообщения `ModuleInstructionService` в байтах (64 КБ). Сообщения, превышающие лимит, отклоняются до попадания в `StreamEngine`. |
| `WS_BACKPRESSURE_SAMPLES_PER_SEC` | `50` | Подсказка обратного давления — возвращается клиенту в поле `max_samples_per_second`. Клиент должен самостоятельно снижать частоту отправки. |
| `WS_BIO_STREAM_MAX_BUFFER_BYTES` | `1048576` | Максимальный размер кольцевого буфера биометрических сэмплов на одну сессию в байтах (1 МБ). Больше инструкционного — поток плотнее. При переполнении новые сэмплы вытесняются, счётчик уходит в `dropped_count` ответа. |
| `WS_BIO_STREAM_MAX_SESSIONS` | `1000` | Максимальное количество одновременных биометрических сессий с активными буферами. Защита от исчерпания памяти при пиковой нагрузке. |
| `WS_BIO_BACKPRESSURE_SAMPLES_PER_SEC` | `50` | Подсказка обратного давления для биометрического потока — возвращается клиенту в поле `max_samples_per_second` ответа `BioStreamAck`. |
| `WS_BIO_STREAM_FLUSH_INTERVAL_MS` | `5000` | Интервал периодического сброса биометрического буфера в таблицу `bio_session_samples`. |
| `WS_RATE_LIMIT_ACTIVITY_START_PER_MIN` | `10` | Максимальное количество `activity:start` от одного пользователя за окно `WS_RATE_LIMIT_WINDOW_MS`. |
| `WS_RATE_LIMIT_WINDOW_MS` | `60000` | Длина окна rate limiting в мс. |
| `SUGGESTIONS_COMPLEXITY_THRESHOLD` | `50` | Допустимое превышение сложности сессий над `maxCompletedComplexity` при формировании рекомендаций (см. [Рекомендации](../breath/suggestions.md)). |
| `LOG_LEVEL` | `info` | Минимальный уровень логирования. Допустимые значения: `error`, `warn`, `info`, `verbose`, `debug`, `silly`. |

## Keep-alive для телефонных медитаций

Watchdog пропускает сессию, если `activeStreamRegistry.hasLiveSubscriber(userId)` возвращает `true` — то есть если к потоку пользователя открыто хотя бы одно активное gRPC-соединение. Это позволяет медитации на телефоне продолжаться неограниченно долго: пока приложение удерживает стрим открытым, `lastActivityAt` может не обновляться, и тем не менее watchdog оставит сессию нетронутой.

30-секундный `WS_RECONNECT_GRACE_MS` намеренно остаётся коротким: пока стрим жив, grace period практически не задействован, а большое значение grace всё равно не спасёт от многоминутного фонового suspension — именно для этого и предназначен keep-alive через `hasLiveSubscriber`.

Подробнее о состояниях сессии и переходах между ними — в [Жизненный цикл сессии](session-lifecycle.md).
