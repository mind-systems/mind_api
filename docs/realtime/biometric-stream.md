# Realtime — Биометрический поток

Биометрический поток — это непрерывная запись показаний датчиков (пульс, NFB-классификатор, эмоциональные состояния и всё, что появится у устройства). Поток привязывается к **корневой сессии** — оси биоданных, которая живёт всё время, пока приложение открыто. Дочерние сессии (практики) биоданными не владеют: аналитика нарезает корневой поток по временным окнам каждой практики.

## Назначение

Записать, как организм пользователя реагировал на то, что в каждый момент времени происходило в практике. Аналитика читает `bio_session_samples` по `rootSessionId` и применяет временно́й join к дочерним сессиям: для любого интервала `[child.startedAt, child.endedAt]` можно выбрать биосэмплы корня, попавшие в это окно, и сопоставить их с инструкциями той же дочерней сессии.

## Когда поток разрешён

Биосэмплы принимаются после того, как сервер разрешил корневую сессию пользователя. Пауза дочерней сессии не блокирует приём биоданных.

`session_id` в каждом батче обязан совпадать с id **корневой** сессии пользователя. Корневой id отличается от id дочерней сессии: `session:state.moduleSessionId` после `activity:start` несёт id **дочерней** сессии, а не корня. Корневой id передаётся сервером в `session:state.moduleSessionId` только тогда, когда при переподключении активная дочерняя сессия отсутствует — в этом случае сервер возвращает состояние самого корня. В остальном клиент обязан сохранить корневой id при первом его появлении (подробнее — в [Протоколе](protocol.md)).

Один клиент держит ровно одно gRPC-соединение биострима — параллельно с инструкционным и sync-стримами. Все три соединения существуют независимо и закрываются вместе при отзыве auth-сессии.

### Коды ошибок приёма

| Код | Условие |
|-----|---------|
| `NO_ROOT_SESSION` | Корневую сессию не удалось разрешить — защитный guard на случай, если создание корня завершилось ошибкой. |
| `SESSION_MISMATCH` | `session_id` в батче не совпадает с id корневой сессии пользователя (например, клиент передал id дочерней сессии). |

## Форма сэмпла

Конверт `BioSample` универсальный — транспорту всё равно, какого типа полезная нагрузка:

| Поле | Описание |
|------|----------|
| `session_id` | Id корневой сессии пользователя. Клиент получает его из `session:state.moduleSessionId` при переподключении без активной дочерней сессии и обязан сохранить для дальнейших батчей. |
| `timestamp` | Клиентское unix-время в мс — момент производства сэмпла датчиком, а не момент отправки батча. |
| `sample_type` | Свободная строка-дискриминатор. Текущие значения: `cardio`, `nfb`, `emotions`. |
| `data` | Произвольная JSON-структура (`google.protobuf.Struct`). Форма зависит от `sample_type` и контролируется клиентом — сервер не валидирует поля внутри `data`. |

Схему `data` под каждый `sample_type` владеет производитель — мобильное приложение. Добавление нового типа не требует изменения proto или сервера: клиент начинает слать новый `sample_type`, и он сохраняется как есть.

## Батчинг

Сэмплы отправляются пачками, а не по одному — частоты до десятков сэмплов в секунду делают пер-сэмпловые RPC-кадры неэффективными. Каждый запрос несёт `BioSampleBatch` с массивом `BioSample`. Сервер отвечает одним `BioStreamAck` на батч.

Внутри батча действуют два правила консистентности:

- Все сэмплы обязаны нести один и тот же `session_id`. Иначе — `INVALID_ARGUMENT` с сообщением `Inconsistent sessionId in batch`.
- Каждый сэмпл обязан нести непустой `sample_type`. Иначе — `INVALID_ARGUMENT` с сообщением `Missing sampleType`.

Пустой батч и пустой `session_id` тоже отвергаются как `INVALID_ARGUMENT`. Нарушение любого правила консистентности останавливает обработку всего батча — частичный приём не предусмотрен.

## Семантика паузы

Сервер принимает любой батч для живой корневой сессии независимо от состояния дочерних сессий и флага `isPaused` — `data` сохраняется в jsonb как есть. Политика приёма сэмплов во время паузы **принадлежит клиенту**: мобильное приложение само решает, какие сэмплы производить и когда.

Сервер ведёт две независимые временны́е шкалы паузы:

- **Серверные маркеры `session_event`** (`PAUSED` / `RESUMED`) — wall-clock журнал жизненного цикла. Проставляются сервером с серверным таймстэмпом при командах `activity:pause` / `activity:resume` и остаются авторитетным источником паузы для аналитики.
- **Клиентские маркеры `breath_phase`** — клиент вставляет маркер паузы с `data.offsetMs` в поток инструкций, образуя паузную полосу `[маркер phase='pause' → следующий реальный маркер фазы]`. При возобновлении клиент не отправляет отдельный `phase='resume'` — он просто возобновляет поток реальных фаз дыхания; приход первой такой фазы закрывает паузную полосу.

Эти две шкалы намеренно **не** объединяются по времени на сервере.

## Подтверждения и backpressure

На каждый принятый батч сервер отвечает `BioStreamAck`:

| Поле | Описание |
|------|----------|
| `session_id` | Id корневой сессии из батча. |
| `received_count` | Накопленное за время соединения количество принятых сэмплов. |
| `dropped_count` | Накопленное за время соединения количество сброшенных сэмплов (переполнение буфера). |
| `max_samples_per_second` | Подсказка обратного давления — рекомендуемая частота отправки. Клиент обязан соблюдать. |
| `timestamp` | Серверное unix-время в мс момента ответа. |

Сервер не дросселирует соединение принудительно. При превышении `max_samples_per_second` клиент сам обязан замедлиться; иначе сэмплы начнут вытесняться из буфера и попадут в `dropped_count`. Любой ненулевой `dropped_count` отражается в логах сервера предупреждением.

## Буферизация и сброс

Принятые сэмплы накапливаются в кольцевом буфере в памяти — по одному буферу на `rootSessionId`. Размер буфера ограничен `WS_BIO_STREAM_MAX_BUFFER_BYTES` (1 МБ по умолчанию). Сэмплы, не помещающиеся в оставшийся объём, сбрасываются и счётчик `dropped_count` инкрементируется.

Буфер сбрасывается в таблицу `bio_session_samples` в трёх случаях:

- по таймеру каждые `WS_BIO_STREAM_FLUSH_INTERVAL_MS` (5 секунд по умолчанию);
- когда корневая сессия переходит в `abandoned` — по истечении grace-периода после разрыва стрима;
- при плановой остановке процесса (`onApplicationShutdown`).

Завершение дочерней сессии (`completed`, `interrupted`) буфер биоданных не сбрасывает — корень продолжает жить.


## Связь с инструкционным потоком

Биострим и инструкционный стрим — два независимых канала с разными точками привязки.

Биострим привязывается к **корневой** сессии: один корень — один буфер — одна строка `bio_session_samples` на батч.

Инструкционный стрим привязывается к **дочерней** сессии: каждая практика накапливает сэмплы инструкций в своём буфере.

При одном открытом приложении одновременно могут идти: один корень с биопотоком и несколько дочерних сессий с собственными инструкционными потоками. Отзыв auth-сессии закрывает все три gRPC-соединения единым `closeAll`.
