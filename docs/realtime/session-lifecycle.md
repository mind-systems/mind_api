# Realtime — Жизненный цикл сессии

`ModuleSession` существует независимо от gRPC-стрима. Стрим может разрываться и восстанавливаться — сессия при этом остаётся в базе данных и может быть продолжена. Без этого любое переключение сети прерывало бы каждую практику.

В системе два типа сессий с разным жизненным циклом: **корневые (root)** и **дочерние (child)**.

## Состояния

`ModuleSession` проходит через шесть состояний — одинаковых для обоих типов:

| Статус | Описание |
|--------|----------|
| `active` | Сессия идёт, пользователь подключён. |
| `disconnected` | Стрим разорван, сессия ещё не закрыта; запущен grace-таймер. |
| `resumed` | Сессия возобновлена после переподключения в grace-периоде. |
| `completed` | Сессия завершена чисто через `activity:end` (только для дочерних). |
| `interrupted` | Пользователь явно прервал сессию через `activity:stop` (только для дочерних). |
| `abandoned` | Grace-период истёк без переподключения. `endedAt` выставляется равным `disconnectedAt` — моменту разрыва, а не моменту истечения grace, чтобы длительность не раздувалась на ширину grace-окна. |

## Жизненный цикл корневой сессии

### Создание

Корень — обычная модуль-сессия типа `root`, которую клиент открывает той же командой, что и практику: `activity:start { activity_type: ROOT }`. Создание идемпотентно по пользователю — повторный `activity:start { ROOT }` возвращает существующий корень, а не создаёт второй. Клиент узнаёт id корня из ответа на эту команду и отличает его по `activity_type === root`. Сервер дополнительно гарантирует корень при подключении (для потоков без явной активности — например, голый биопоток), так что корень всегда есть к моменту, когда он нужен.

### Подключение и reconnect

При открытии стрима `ModuleStateService` аутентифицирует соединение и проверяет наличие корневой сессии:
- Корень найден в статусе `disconnected` → он немедленно возобновляется: статус меняется на `active`, grace-таймер корня отменяется.
- Корень не найден → создаётся новый.

### Разрыв соединения

При разрыве стрима корневая сессия переходит в `disconnected` и запускается её собственный grace-таймер (`WS_RECONNECT_GRACE_MS`). Дочерние сессии при этом не затрагиваются — у каждой свой grace-таймер.

Разрыв и восстановление соединения — свойство транспорта, то есть корня: одно соединение роняет корень и всех его детей разом. Поэтому в поток инструкций корня пишется **один** маркер `disconnected` (в момент разрыва) и **один** маркер `reconnected` (при возвращении в grace-период) — на уровне корня, а не на каждом ребёнке. Это первые записи `session_stream_samples`, привязанные к корневому id. Дочерняя сессия объясняет свой пробой во входных данных, читая connection-события корня, перекрывающие её окно `[startedAt, endedAt]`.

### Завершение

Корневая сессия **не завершается командой**: `activity:end`/`activity:stop`, адресованные корню, отвергаются кодом `CANNOT_END_ROOT` (эти команды применимы только к дочерним сессиям). Корень уходит в `abandoned` когда:
- истёк его grace-таймер после разрыва стрима, или
- janitor подобрал пустой корень — без дочерних сессий, простаивающий дольше `WS_EMPTY_ROOT_TTL_MS` и без живого соединения.

Живой корень janitor не трогает. Одно лишь наличие биоданных тоже не защищает корень — только активная дочерняя сессия.

## Жизненный цикл дочерней сессии

### Создание

Клиент отправляет `activity:start`. `ActivityEngine` создаёт запись `ModuleSession` с `rootSessionId` = id текущего корня, фиксирует время начала и тип активности.

Повторный `activity:start` с тем же `client_activity_id` — это **идемпотентный запрос**: сервер обнаруживает недавно созданную дочернюю сессию по паре `(userId, client_activity_id)` и возвращает её `session:state` без создания новой записи. Защита работает в коротком временном окне, рассчитанном на сетевые ретраи. Если `client_activity_id` новый или окно истекло — открывается **вторая параллельная дочерняя сессия**; одновременная работа нескольких дочерних сессий допустима.

### Поток инструкций

Пока дочерняя сессия активна, клиент отправляет сэмплы инструкций через `ModuleInstructionStreamService`. `StreamEngine` складывает сэмплы в кольцевой буфер и сбрасывает их в `session_stream_samples` каждые 5 секунд или при завершении дочерней сессии.

### Разрыв соединения

Каждая дочерняя сессия имеет **независимый** grace-таймер по своему `sessionId`. Разрыв стрима или открытие стрима с нового устройства не отменяет grace-таймеры параллельно идущих дочерних сессий.

### Reconnect и grace-период

Если пользователь переподключается в течение grace-периода, сервер обнаруживает незавершённую дочернюю сессию, отменяет её таймер и вызывает `ActivityEngine.resumeActivity()`. Клиент получает `session:state` с `status: resumed`.

Клиент может опционально передать `module-session-id` в gRPC metadata. Если такая сессия найдена в БД со статусом `abandoned` (например, была уничтожена watchdog-ом во время фонового suspension) — сервер немедленно возвращает `session:state` с `status: abandoned`. Это позволяет клиенту детектировать завершение сессии за кадром и корректно обновить UI.

### Пауза и возобновление

`activity:pause` устанавливает `isPaused = true` в in-memory состоянии дочерней сессии и записывает маркер `paused` в поток инструкций. `activity:resume` снимает флаг и записывает `resumed`. Эти маркеры — дискретные `session_event` и персистятся **немедленно**, отдельной строкой `session_stream_samples`, а не ждут планового сброса буфера.

Пауза принадлежит клиенту: её меняют только команды `activity:pause` / `activity:resume`. Сервер не сбрасывает флаг сам — ни при разрыве, ни при reconnect. При переподключении в grace-периоде сессия возвращается с тем же `isPaused`, что был до разрыва, и кадр `session:state` сообщает его **фактическое** значение; следующий `activity:resume` поставленной на паузу сессии проходит штатно.

Отдельной колонки паузы в БД нет. После перезапуска сервера `isPaused` каждой сессии **выводится** из её последнего маркера `paused`/`resumed` в `session_stream_samples` — поэтому пауза переживает рестарт.

Коды ошибок: `no_active_session`, `already_paused`, `not_paused`.

### Прерывание и завершение

`activity:stop` — принудительная остановка конкретной дочерней сессии. Сервер выставляет статус `interrupted` и `endedAt`. Прерванные сессии засчитываются в статистику, если длительность превышает `WS_MIN_SESSION_DURATION_S`.

`activity:end` — штатное завершение дочерней сессии. Сервер немедленно выставляет статус `completed` и `endedAt`.

Обе команды принимают опциональный `session_id` для адресации конкретного дочернего узла (подробнее — в [Протоколе](protocol.md)).

## Восстановление после перезапуска сервера

При старте сервер **восстанавливает** in-memory стор, а не бросает все сессии. Он загружает `ModuleSession` со статусом `active` или `disconnected`, заново собирает `ActivitySessionStore` (`{ rootSessionId, children }`, связывая детей с корнем по `rootSessionId`), помечает каждую сессию `disconnected` с `disconnectedAt = lastActivityAt` и выводит `isPaused` каждой из последнего маркера `paused`/`resumed` в `session_stream_samples`.

Для каждой восстановленной сессии заводится grace-таймер, отсчитываемый **от момента старта процесса** — так у любого клиента есть полное grace-окно на возвращение, независимо от длительности простоя. Клиент, переподключившийся в этом окне, возобновляет сессию обычным путём (`handleReconnect` отменяет таймер и пишет маркер `reconnected`). Сессия, чей клиент не вернулся, уходит в `abandoned` тем же grace-таймером, что и при обычном разрыве (`endedAt = disconnectedAt`, маркер + события).
