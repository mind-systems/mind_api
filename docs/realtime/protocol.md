# Realtime — Протокол

Клиент устанавливает три независимых gRPC bidi-стрима: `ModuleStateService` для управления состоянием активности, `ModuleInstructionStreamService` для потоковой передачи инструкций и `ModuleBiometricStreamService` для потоковой передачи биометрических сэмплов. Все сервисы используют JWT-аутентификацию: токен передаётся в metadata при открытии стрима. Соединение отклоняется, если токен отсутствует, истёк или не найден в таблице `user_sessions`.

Протокол `ModuleBiometricStreamService` описан отдельно в [Биометрическом потоке](biometric-stream.md); этот документ покрывает первые два сервиса.

## `ModuleStateService`

Управляет жизненным циклом активности. Клиент отправляет команды, сервер отвечает состоянием.

**Команды клиента → сервер:**

| Команда | Описание |
|---------|----------|
| `activity:start` | Начало активности. Payload: `activityType` (например `breath`) и опциональный `activityRefId` — привязка к конкретной записи без жёсткого FK. |
| `activity:end` | Чистое завершение. Сервер немедленно выставляет статус `completed`. |
| `activity:stop` | Принудительная остановка пользователем. Сервер выставляет статус `interrupted`. |
| `activity:pause` | Пауза активной сессии. Сервер фиксирует `isPaused = true` в in-memory состоянии. |
| `activity:resume` | Снятие с паузы. Сервер снимает `isPaused`. |

**Ответы сервера → клиент:**

| Ответ | Описание |
|-------|----------|
| `session:state` | Отправляется при подключении и после каждой команды. Payload: `moduleSessionId`, `status`, `isPaused`. При подключении с незавершённой сессией в grace-периоде — `status: resumed`. |
| `session:error` | Ошибка протокола или бизнес-логики. Содержит `code`, `message`, `timestamp`. |

## `ModuleInstructionStreamService`

Принимает поток инструкций, которые модуль выдаёт пользователю в реальном времени. Каждый сэмпл — запись о том, что именно показывало приложение в конкретный момент. Сервис намеренно отделён от `ModuleStateService`, чтобы управляющие команды не конкурировали с потоком данных.

**Сэмплы клиент → сервер:**

| Поле | Описание |
|------|----------|
| `session_id` | Идентификатор активной сессии из `session:state.moduleSessionId`. |
| `module_id` | Идентификатор модуля-отправителя, например `breath`. |
| `instruction_type` | Тип инструкции, определяется модулем, например `breath_phase`. |
| `data` | Payload инструкции — свободная структура. Схема зависит от `module_id` и `instruction_type`. |
| `timestamp` | Клиентское unix-время в мс — момент выдачи инструкции. |

**Подтверждения сервера → клиент:**

| Поле | Описание |
|------|----------|
| `received_count` | Суммарное количество принятых сэмплов в текущем стриме. |
| `dropped_count` | Суммарное количество сброшенных сэмплов (переполнение буфера). |
| `max_samples_per_second` | Рекомендуемый лимит частоты отправки. Клиент обязан его соблюдать. |

## Rate limiting

Только `activity:start` подпадает под rate limiting — на уровне контроллера. Остальные команды `ModuleStateService` не ограничиваются.

| Переменная | По умолчанию | Описание |
|------------|-------------|----------|
| `WS_RATE_LIMIT_ACTIVITY_START_PER_MIN` | `10` | Максимальное число `activity:start` от одного пользователя за окно. |
| `WS_RATE_LIMIT_WINDOW_MS` | `60000` | Длина окна в мс. |

При превышении клиент получает `session:error` с кодом `RATE_LIMIT_EXCEEDED`.
