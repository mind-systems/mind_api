# Realtime — Протокол

Клиент устанавливает три независимых gRPC bidi-стрима: `ModuleStateService` для управления состоянием активности, `ModuleInstructionStreamService` для потоковой передачи инструкций и `ModuleBiometricStreamService` для потоковой передачи биометрических сэмплов. Все сервисы используют JWT-аутентификацию: токен передаётся в metadata при открытии стрима. Соединение отклоняется, если токен отсутствует, истёк или не найден в таблице `user_sessions`.

Протокол `ModuleBiometricStreamService` описан отдельно в [Биометрическом потоке](biometric-stream.md); этот документ покрывает первые два сервиса.

## `ModuleStateService`

Управляет жизненным циклом активности. Клиент отправляет команды, сервер отвечает состоянием.

**Команды клиента → сервер:**

| Команда | Описание |
|---------|----------|
| `activity:start` | Начало дочерней активности. Payload: `activityType` (например `breath`), опциональный `activityRefId` — привязка к конкретной записи без жёсткого FK, и опциональный `client_activity_id` — токен идемпотентности. |
| `activity:end` | Чистое завершение дочерней сессии. Сервер немедленно выставляет статус `completed`. Принимает опциональный `session_id` — id целевой дочерней сессии. |
| `activity:stop` | Принудительная остановка дочерней сессии. Сервер выставляет статус `interrupted`. Принимает опциональный `session_id`. |
| `activity:pause` | Пауза дочерней сессии. Принимает опциональный `session_id`. |
| `activity:resume` | Снятие с паузы дочерней сессии. Принимает опциональный `session_id`. |

### Адресация дочерних сессий (`session_id`)

Команды `activity:end`, `activity:stop`, `activity:pause`, `activity:resume` принимают опциональный `session_id` — id конкретной дочерней сессии, которую нужно затронуть.

- Если `session_id` указан — сервер адресует именно эту дочернюю сессию.
- Если `session_id` не указан и у пользователя ровно одна активная дочерняя сессия — она используется как цель.
- Если `session_id` не указан, а активных дочерних сессий несколько — сервер отвечает `session:error` с кодом `AMBIGUOUS_SESSION`.

### Идемпотентность `activity:start` (`client_activity_id`)

Опциональный `client_activity_id` позволяет клиенту безопасно ретраить `activity:start` без риска открыть дублирующую дочернюю сессию. Если в короткое временное окно сервер получает повторный `activity:start` с тем же `(userId, client_activity_id)`, он возвращает `session:state` уже созданной дочерней сессии вместо открытия новой.

Если `client_activity_id` новый или окно ретрая истекло — открывается **новая** дочерняя сессия. Одновременное существование нескольких дочерних сессий допустимо.

**Ответы сервера → клиент:**

| Ответ | Описание |
|-------|----------|
| `session:state` | Отправляется в ответ на команду и при возобновлении дочерней сессии на reconnect. Payload: `moduleSessionId`, `status`, `isPaused`, `activityType`. При reconnect с дочерней сессией в grace-периоде — `status: resumed`. |
| `session:error` | Ошибка протокола или бизнес-логики. Содержит `code`, `message`, `timestamp`. |

Отдельного кадра корня на подключение нет. Клиент открывает корневую сессию командой `activity:start { activity_type: ROOT }` и получает её `session:state` с `activity_type: ROOT` и `moduleSessionId` = id корня — тем же путём «запрос → ответ», что и для практики. Корень отличается от дочерней сессии **по `activity_type` (`ROOT` против типа практики)**; клиент сохраняет корневой id для последующих батчей биострима и корневых меток (подробнее — в [Биометрическом потоке](biometric-stream.md)).

Каждый `session:state` несёт `activity_type` своей сессии: кадр корня — `ROOT`, кадры дочерних сессий — тип практики (`breath`, `meditation`). `moduleSessionId` дочернего кадра — id **дочерней** сессии.

## `ModuleInstructionStreamService`

Принимает поток инструкций, которые модуль выдаёт пользователю в реальном времени. Каждый сэмпл — запись о том, что именно показывало приложение в конкретный момент. Сервис намеренно отделён от `ModuleStateService`, чтобы управляющие команды не конкурировали с потоком данных.

**Сэмплы клиент → сервер:**

| Поле | Описание |
|------|----------|
| `session_id` | Id любой живой сессии пользователя — дочерней (`session:state.moduleSessionId` после `activity:start`) или корневой (id из ответа на `activity:start { ROOT }`). |
| `module_id` | Идентификатор модуля-отправителя, например `breath`. |
| `instruction_type` | Тип инструкции, определяется модулем, например `breath_phase`. |
| `data` | Payload инструкции — свободная структура. Схема зависит от `module_id` и `instruction_type`. |
| `timestamp` | Клиентское unix-время в мс — момент выдачи инструкции. |

Сервер принимает сэмпл, если `session_id` — это **живая сессия, принадлежащая пользователю** (любая из его дочерних сессий либо его корень). Это позволяет вести потоки инструкций нескольких параллельных практик одновременно и помечать корневые метки id корня. `session_id`, не принадлежащий пользователю или не живой, отвергается кодом `SESSION_NOT_FOUND`; пустой `session_id` — `INVALID_ARGUMENT`. Сервер не требует, чтобы `session_id` указывал на единственную активную практику.

**Подтверждения сервера → клиент:**

| Поле | Описание |
|------|----------|
| `received_count` | Суммарное количество принятых сэмплов в текущем стриме. |
| `dropped_count` | Суммарное количество сброшенных сэмплов (переполнение буфера). |
| `max_samples_per_second` | Рекомендуемый лимит частоты отправки. Клиент обязан его соблюдать. |

## Rate limiting

Только `activity:start` подпадает под rate limiting — на уровне контроллера. Остальные команды `ModuleStateService` не ограничиваются.

| Переменная | По умолчанию | Описание |
|------------|-------------|----------|
| `WS_RATE_LIMIT_ACTIVITY_START_PER_MIN` | `10` | Максимальное число `activity:start` от одного пользователя за окно. |
| `WS_RATE_LIMIT_WINDOW_MS` | `60000` | Длина окна в мс. |

При превышении клиент получает `session:error` с кодом `RATE_LIMIT_EXCEEDED`.
