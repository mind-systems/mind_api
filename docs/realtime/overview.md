# Realtime — Обзор архитектуры

Realtime-канал открывается при старте приложения и живёт до его закрытия. Через него проходят все команды управления активностью и поток инструкций модуля. Соединение установлено заранее — начать практику можно без дополнительного рукопожатия.

## Ключевое разделение: транспорт и сессия

gRPC-стрим и доменная сессия — разные сущности. Стрим — это транспорт; `ModuleSession` — доменный объект с собственным жизненным циклом. Разрыв стрима не означает конца сессии: она продолжает существовать в базе данных в состоянии `disconnected`, пока не истечёт grace-период или не придёт новое соединение от того же пользователя. Без этого разделения любой LTE→WiFi переход или фоновая оптимизация ОС прерывала бы сессию и портила статистику.

## Двухуровневая модель сессий

Для каждого пользователя в системе существует два уровня сессий.

**Корневая сессия (root)** — непрерывная «ось биоданных» на всё время, пока приложение открыто; это обычная модуль-сессия типа `root`, одна на пользователя. Клиент открывает и адресует её той же командой, что и практику — `activity:start { activity_type: ROOT }` (идемпотентно по пользователю: повторный запрос возвращает тот же корень) — и узнаёт её id из ответа. Сервер дополнительно гарантирует корень при подключении, чтобы биопоток работал и без явной активности. Корень не завершается командой: `activity:end`/`activity:stop` на него отвергается (`CANNOT_END_ROOT`); он уходит в `abandoned` по grace-периоду после разрыва соединения либо подбирается janitor-ом, когда остаётся без дочерних сессий, простаивает дольше `WS_EMPTY_ROOT_TTL_MS` и не имеет живого соединения. Биометрия датчиков хранится под корнем; клиент помечает его id биобатчи и корневые метки.

**Дочерние сессии (child)** — это конкретные практики: дыхание, медитация и любые будущие типы активности. Каждая дочерняя сессия создаётся командой `activity:start`, несёт `rootSessionId` (ссылку на корень) и имеет независимый жизненный цикл с собственным grace-таймером. Несколько дочерних сессий могут идти одновременно — они перекрываются на корневой оси времени. Биоданные аналитика нарезает по временному окну `[child.startedAt, child.endedAt]`, читая их из корня.

Инвариант системы: **один корень + N параллельных дочерних сессий на пользователя**.

## Слои системы

**Transport Layer** — `ModuleStateGrpcController`, `ModuleInstructionStreamGrpcController`, `ModuleBiometricStreamGrpcController`. Отвечает только за протокол: маршрутизацию входящих сообщений и отправку исходящих. Аутентификация вынесена в `GrpcAuthInterceptor` — проверяет JWT из metadata и наличие сессии в `user_sessions` до обработки каждого запроса.

**Activity Layer** — `ActivityEngine`, доменное ядро. Управляет жизненным циклом `ModuleSession`: создаёт и возобновляет корневые сессии, создаёт, завершает и помечает как брошенные дочерние сессии. Здесь живут переходы состояний и grace-таймеры — отдельные для корня и для каждого дочернего узла.

**Instruction Layer** — `StreamEngine`, движок хранения таблицы `session_stream_samples` с двумя источниками. Клиентский поток инструкций (`breath_phase`) аккумулируется в кольцевом буфере в памяти и сбрасывается каждые 5 секунд или при завершении дочерней сессии. Дискретные маркеры жизненного цикла (`session_event`) пишет **сам сервер** при переходах состояния сессии — они не передаются клиентом по инструкционному стриму, а лишь делят с инструкциями таблицу и движок хранения; персистятся немедленно отдельной строкой, чтобы не потеряться при сбое до планового сброса.

**Biometric Layer** — `BiometricStreamEngine` обслуживает биометрические сэмплы по тому же буферному паттерну: отдельный буфер на корневую сессию, отдельные конфиг-ключи (`WS_BIO_*`), отдельная таблица `bio_session_samples`.

**Stats Layer** — `StatsModule`. Подписывается на события завершения дочерних сессий через `EventEmitter2` и обновляет агрегированную статистику пользователя. Корневые сессии в статистику не попадают.

## In-memory состояние

- `ActivitySessionStore` — хранит состояние на пользователя в виде `{ rootSessionId, children: Map<sessionId, …> }`: идентификатор корневой сессии и карту активных дочерних сессий с их типами, временем начала и флагами паузы. Grace-таймеры заведены отдельно для корня и для каждого дочернего узла по его `sessionId`.
- `ActiveStreamRegistry` — Map от `userId` к множеству активных gRPC-подписчиков пользователя. Один юзер держит несколько параллельных стримов (state, instructions, biometric, sync), все они живут как независимые подписчики под одним ключом. `closeAll(userId)` — единая точка принудительного закрытия всех каналов: используется при отзыве auth-сессии.

## Политика одного соединения на каждый сервис

Сервер допускает по одному активному соединению на пользователя в каждом из realtime-сервисов. Если приходит новый стрим того же типа, а старый ещё жив — старый принудительно закрывается. Стримы разных типов сосуществуют параллельно. Это защищает от гонок состояния при переключении сетей, перезапуске приложения или подключении с двух устройств.
