# Realtime — Модель инструкций

Поток инструкций — это лог того, что приложение говорило пользователю делать в каждый момент времени. Без этих меток биометрические данные датчиков теряют смысл: числа есть, но неизвестно, что в этот момент происходило.

## Дочерняя сессия как контейнер инструкций

Инструкционный поток привязан к **дочерней сессии**: `session_id` в сэмпле практики — это id дочернего узла, который задаёт временной горизонт упражнения (`startedAt` — момент нажатия Play, `endedAt` — момент завершения). Сэмплы хранятся в `session_stream_samples` под `moduleSessionId` сессии, указанной в `session_id`.

Поток маршрутизирует каждый сэмпл по `session_id` в **любую живую сессию пользователя**: несколько параллельных практик ведут свои потоки инструкций одновременно (каждая помечает сэмплы своим id), а метки корневого уровня клиент помечает id корня. Сервер проверяет только **принадлежность**: `session_id` должен быть живой сессией этого пользователя (дочерней или корневой); чужой или мёртвый id отвергается кодом `SESSION_NOT_FOUND`. Ограничения «ровно одна активная практика» нет.

## Момент activity:start

`activity:start` должен отправляться **когда пользователь нажал Play**, а не при открытии экрана. `startedAt` должен совпадать с реальным началом упражнения — от точности этой метки зависит корректность time-join с биометрическими данными.

## Форма сэмпла

Каждый сэмпл использует единый конверт независимо от модуля и типа инструкции:

| Поле | Описание |
|------|----------|
| `session_id` | Ссылка на дочернюю `ModuleSession` |
| `module_id` | Идентификатор модуля, например `breath` |
| `instruction_type` | Дискриминатор: `breath_phase`, `session_event`, ... |
| `data` | Свободная структура (Struct/JSONB), форма зависит от `instruction_type` |
| `timestamp` | Клиентское unix-время в мс — момент выдачи инструкции |

### `breath_phase` (пишет клиент)

```json
{ "phase": "exhale", "durationMs": 6000 }
```

Отправляется при каждой смене фазы пока движок активен.

### `session_event` (пишет сервер)

```json
{ "event": "session_started" }
{ "event": "paused" }
{ "event": "resumed" }
{ "event": "session_ended" }
{ "event": "session_abandoned" }
{ "event": "session_interrupted" }
{ "event": "disconnected" }
{ "event": "reconnected" }
```

Lifecycle-события практики (`session_started/paused/resumed/ended/abandoned/interrupted`) пишутся под id **дочерней** сессии при каждом её переходе: `activity:start/pause/resume/end/stop` и по истечении grace period. `session_abandoned` записывается, когда grace period дочерней сессии истёк без переподключения; `session_interrupted` — при явном `activity:stop`.

`disconnected` и `reconnected` — события **уровня соединения** и пишутся под id **корня** (по одному на разрыв и на возвращение), а не на каждом ребёнке. Сервер — авторитетный источник всех этих событий.

Маркеры `session_event` дискретны и **персистятся немедленно**, отдельной строкой `session_stream_samples`, в отличие от непрерывного `breath_phase`, который батчится в буфере и сбрасывается раз в 5 секунд. Поэтому ни одно lifecycle- или connection-событие не теряется при сбое до планового сброса.

## Биометрические данные и временно́й join

Биометрические данные хранятся отдельно — в корневой сессии (подробнее — [Биометрический поток](biometric-stream.md)). Аналитика соотносит биоданные с конкретной практикой через **временное окно**: выбирает строки `bio_session_samples` корневой сессии (`moduleSessionId = child.rootSessionId`) с `ts ∈ [child.startedAt, child.endedAt]`. Точность `startedAt` дочерней сессии определяет качество этого соответствия.

Для любого биометрического сэмпла, попавшего в окно, инструкционный поток той же дочерней сессии даёт контекст: что приложение показывало пользователю в этот момент.

Тем же оконным приёмом практика объясняет пробои в данных: события `disconnected`/`reconnected` корня, перекрывающие `[child.startedAt, child.endedAt]`, показывают, что пропуск фаз и биосэмплов вызван разрывом соединения, а не бездействием пользователя.

## Пауза и инструкции

Когда сессия поставлена на паузу, сервер продолжает принимать любые входящие сэмплы — он не блокирует и не фильтрует `breath_phase`. Политика приёма во время паузы принадлежит клиенту: приложение само вставляет в поток маркер `breath_phase` с `phase='pause'` и перестаёт слать реальные фазы. Lifecycle-события (`paused`, `resumed`) сервер при этом проставляет самостоятельно с серверным таймстэмпом — они проходят всегда. В результате между клиентским маркером паузы и первой реальной фазой после возобновления образуется пробел в сэмплах фаз (та же паузная полоса, что описана в [Биометрическом потоке](biometric-stream.md)).

## Backpressure

Сервер управляет частотой через поле `max_samples_per_second` в подтверждении:

```json
{
  "received_count": 10,
  "dropped_count": 0,
  "max_samples_per_second": 5
}
```

Клиент обязан соблюдать `max_samples_per_second`. Для фаз дыхания это некритично — фаза меняется раз в несколько секунд. Для будущих высокочастотных биометрических потоков (256 Hz ЭЭГ) этот механизм станет ключевым.
