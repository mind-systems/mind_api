## Continuous bio timeline — root session + overlapping activities

Bio data decouples from individual activities and lives on a single continuous **root session** (the "app is open" container) created lazily on the first meaningful event of a stream connection. Activities (breath, meditation) become flat **child sessions** overlaid on that timeline — they no longer own bio data, they slice it by time window (`bio WHERE rootSessionId = R AND ts ∈ [child.startedAt, child.endedAt]`). This removes the one-session-per-user constraint, allows concurrent activities (e.g. breathing inside a meditation), and is the precondition for the `pre → event → post` timeline the coach service needs. Strict per-session lifecycle is preserved; only the single-slot assumption is dropped. Two-level model only (`rootSessionId`, no `parentSessionId`); migration is 1:1 (one synthetic root per existing session); FK is `ON DELETE CASCADE`. Tasks below are strictly sequential — each depends only on those above it.

## Realtime durability — connection-loss visibility + restart recovery

Three correctness gaps surfaced after the bio-timeline refactor: the realtime timeline does not record connection loss (a disconnect/reconnect is invisible to analytics), the server silently mutates pause state it does not own, and a server restart abandons every in-flight session instead of restoring it. The fix rests on one principle: **discrete `SESSION_EVENT` markers** (start/stop/end/abandon/interrupt/pause/resume/disconnect/reconnect) are rare and load-bearing, so they **persist immediately** at emit and a crash cannot lose them; the **continuous instruction/bio streams** stay batched. Pause durability is a *consequence* of this, not a special case — no `module_sessions` pause column, no client/proto change. Four atomic tasks, dependency-ordered: foundational immediate-marker persistence → connection-loss markers → pause-state integrity → rehydrate (which derives pause from the now-durable markers).

## Phase 60 — Persist discrete session-event markers immediately

`StreamEngine.push` buffers every sample — discrete markers and continuous `breath_phase` alike — and persists only on the periodic `flushAll`. A crash before the timer fires silently loses any buffered marker (a STARTED/ENDED/ABANDONED/PAUSED/disconnect can vanish), corrupting the timeline and the restart-derive. Discrete markers are rare and load-bearing; they should be durable the instant they emit.

- [ ] **Persist discrete markers immediately; batch only continuous streams** — in `StreamEngine.push`, branch on the sample kind: `sample.data?.dataType === SESSION_EVENT` → **persist immediately** as a one-element `session_stream_samples` row (`{ moduleSessionId: sid, samples: [sample], flushedAt: now }`), fire-and-forget so `push` stays synchronous and off the client path; everything else (instruction `breath_phase`, whose `data` carries no `dataType`) → buffer + periodic flush exactly as today. Do **not** rename `push` or add a public method (keeps committed `push(...)` assertions valid); markers skip the buffer byte-cap (tiny, rare). The 7 marker emitters in `activity-engine.service.ts` already call `push` — unchanged. No client/proto change. Spec: `.ai-factory/notes/25-persist-ispaused.md`.

## Phase 61 — Annotate connection loss on the root timeline

The timeline has no record of a dropped connection: `onDisconnect`/`resumeActivity` write no instruction marker, so a child's `breath_phase`/bio gap during a disconnect is indistinguishable from the user being idle, and a grace-abandoned session records `endedAt = now` (grace expiry), inflating its duration by the grace window. Connection loss is a property of the **root** (one transport drops root + all children together), so it is annotated once on the root, never per child. The markers are `SESSION_EVENT`, so Phase 60 makes them durable for free.

- [ ] **Disconnect/reconnect markers on the root + accurate abandon timestamp** — add `DISCONNECTED`/`RECONNECTED` to `StreamSessionEvent` and push them **once to the root id** from the connection-level handlers `handleTransportDisconnect`/`handleReconnect` (not the per-session `onDisconnect`/`resumeActivity`, which fire per child → would spam). These are the first root-keyed entries in `session_stream_samples`; a child explains its gap by reading the root's connection events overlapping its `[startedAt, endedAt]` window. In `abandonActivity`, set `endedAt = disconnectedAt` instead of `now`. `session_event` is free-form jsonb — no proto change, producing client untouched; only timeline readers (web dashboard, coach) gain two optional event values. Spec: `.ai-factory/notes/23-connection-loss-markers.md`.

## Phase 62 — Pause-state integrity across reconnect

The server silently mutates pause state it does not own: `resumeActivity` resets `state.isPaused = false` on **every** reconnect (`activity-engine.service.ts:573`) and the reconnect `session:state` reports `is_paused = false` hardcoded — so a session the user paused comes back unpaused without any command from the user, and a subsequent `unpause` is rejected `NOT_PAUSED`. Pause/unpause is client-owned; the server must never change it on its own. (Marker durability is Phase 60's concern; restart-survival comes from deriving pause from the durable marker in Phase 63.)

- [ ] **Stop the server self-mutating pause** — `resumeActivity` resets `state.isPaused = false` on every reconnect (`activity-engine.service.ts:573`) and the reconnect `session:state` reports `isPaused: false` hardcoded (`module-state.grpc.controller.ts:142`), so a paused session silently comes back active and the next `activity:resume` hits `NOT_PAUSED`. Remove the reset; report the resumed session's **actual** `isPaused`, surfaced through `ActivityEngine` (the controller has no store dep; never read it off the returned entity). Touch nothing in the `pause`/`unpause` guards. No column, no proto change. Spec: `.ai-factory/notes/24-pause-state-integrity.md`.

## Phase 63 — Rehydrate realtime state on restart

`StartupRecoveryService` abandons every `ACTIVE`/`DISCONNECTED` session on boot, so a server restart (graceful or crash) severs all in-flight work: a returning client cannot resume (the in-memory store is empty, so `handleReconnect` finds nothing) and `ensureRoot` mints a fresh root, splitting an ongoing practice in two. All durable state lives in `module_sessions` (and pause in the durable `PAUSED`/`RESUMED` marker made crash-safe by Phase 60) — recovery should rebuild the store, not discard it.

- [ ] **Rehydrate the session store instead of abandoning** — on bootstrap, load `module_sessions` with `status ∈ {ACTIVE, DISCONNECTED}`, rebuild the `Map<userId, {rootSessionId, children}>` store (linking by `rootSessionId`, deriving `isPaused` from each child's last `PAUSED`/`RESUMED` marker in `session_stream_samples`), mark each `DISCONNECTED` (`disconnectedAt = lastActivityAt`) and arm a grace timer **from process start** so any client gets a full window to return regardless of downtime. Reconnect resumes via the existing `handleReconnect` path (cancels grace, `RECONNECTED` marker); sessions whose client never returns are abandoned consistently by the existing grace timer (`abandonActivity` — marker + events), replacing today's silent bulk abandon. New ctor `StartupRecoveryService(repo, streamSampleRepo, activitySessionStore, activityEngine)`; no new table, no shutdown status writes. Spec: `.ai-factory/notes/26-state-rehydration.md`.
