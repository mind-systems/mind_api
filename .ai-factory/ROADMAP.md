## Phase 16 — Feature: BciDevice resource

Scope: gRPC only (no REST). BCI is intentionally **not** wired into the realtime stream pipeline and is **not** propagated through the `sync` changes journal (`src/sync/`, `src/changelog/`) — paired-device lists are not synced across a user's phones; each phone calls `Register` on first pairing locally.

- [x] **`BciDeviceService`** — Create `src/bci/bci-device.service.ts` with three methods. `listForUser(userId: string): Promise<BciDevice[]>` — returns rows for the user ordered by `updated_at DESC` so the most recently used device is first. `register(userId: string, serial: string): Promise<BciDevice>` — idempotent: if a row with the same `(userId, serial)` exists, **force-bump `updated_at` to the current time** and return the reloaded row; otherwise insert a new row. Important: `@UpdateDateColumn` is only refreshed by TypeORM when `.save()` detects a real change to the entity — calling `repo.save(existingRow)` unchanged will **not** move the timestamp, which breaks the `List` ordering for the exact case it exists for (re-registering the most-recently-used device). Use one of these two patterns explicitly: (a) `await repo.update({ userId, serial }, { updatedAt: () => 'CURRENT_TIMESTAMP' })` followed by `repo.findOneByOrFail({ userId, serial })`, or (b) load the row, set `row.updatedAt = new Date()` manually, then `repo.save(row)`. Implementation must be safe against the unique-constraint race (catch the unique-violation `QueryFailedError` and re-fetch — Postgres error code `23505`). `delete(userId: string, id: string): Promise<void>` — fetch by `id`; if not found throw `RpcException({ code: GrpcStatus.NOT_FOUND, message: 'BCI device not found' })`; if `row.userId !== userId` throw `RpcException({ code: GrpcStatus.PERMISSION_DENIED, message: 'BCI device belongs to another user' })`; otherwise delete. Ownership checks live here, not in the controller. Imports: `RpcException` from `@nestjs/microservices`, `status as GrpcStatus` from `@grpc/grpc-js` — same imports used in `src/realtime/sync-stream.grpc.controller.ts`. [8m 2s]

## Phase 18 — Fix: flush buffers on session-revoke

Currently if `ModuleStateGrpcController.handleSessionRevoked` catches an error from `stopActivity`, no `SessionEvents.INTERRUPTED` is emitted → engines don't flush → `closeAll` terminates streams → in-memory buffers wait for the next periodic flush or die with the process. Phase 19 doubles the loss surface (biometric buffers). Fix is a new `SessionEvents.REVOKED` event emitted unconditionally from the revoke handler; both engines flush on it. Full spec: `.ai-factory/notes/04-session-revoke-flush-fix.md`.

- [x] **Add `SessionEvents.REVOKED` to enum** — Append `REVOKED: 'session.revoked'` to `src/realtime/events/session.events.ts`. Standalone — no consumer yet. [2m 42s]

- [x] **Emit `REVOKED` from `handleSessionRevoked` — only on `stopActivity` failure** — Per note 04 §"Emit-only-in-catch". Inject `EventEmitter2` into `ModuleStateGrpcController`. Resolve `sessionId = activityEngine.getActiveSession(userId)?.sessionId` **before** `stopActivity` (which may clear in-memory state). Run `try { await stopActivity }`; **inside the catch** (and only there) — if `sessionId` was non-null, emit `SessionEvents.REVOKED, { sessionId }`. Then `closeAll(userId)`. Reason emit is catch-only: on happy path `ActivityEngine.stopActivity` already emits `SessionEvents.INTERRUPTED` at the last line; a second unconditional `REVOKED` emit would race with the in-flight `flush` (handler-A slices `buffer.samples`, `await save` in flight, handler-B slices the same non-empty array → two inserts of identical sample batches into `session_stream_samples` and after Phase 19 into `bio_session_samples`). Catch-only means only failure paths — where `INTERRUPTED` was never reached — emit `REVOKED`. [11m 49s]

- [x] **`StreamEngine.onSessionRevoked` handler** — Add `@OnEvent(SessionEvents.REVOKED) async onSessionRevoked(payload: { sessionId: string })` to `src/realtime/services/stream-engine.service.ts` — copy/paste body of `onSessionInterrupted` (flush + delete buffer), only change the log message. [3m 45s]

## Phase 20 — Feature: NFB Calibration History

Mobile clients use the latest valid record to restore the native classifier without re-calibrating; the full history enables long-term tracking of individual alpha drift. Architectural spec: `mind_mobile/.ai-factory/notes/30-nfb-calibration-history.md`.
