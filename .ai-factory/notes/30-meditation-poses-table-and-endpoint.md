# Meditation Poses — Server Table and REST Endpoint

**Date:** 2026-06-03
**Source:** bug investigation + product discussion

---

## Background

The meditation module tracks which pose the user chose during a session. This pose ID is recorded in `module_sessions.activityRefId` — the same column that stores the breath session UUID for `BREATH` activity type. The column is typed `uuid` in PostgreSQL.

The mobile app currently has six poses hardcoded as plain string slugs (`'easy'`, `'lotus'`, etc.). When a meditation session starts, the app was sending the slug directly as `ref_id` in the `ActivityStartCmd` gRPC command, which caused:

```
error: invalid input syntax for type uuid: "easy"
```

The session was never written to the database. All meditation biometric data was lost.

The fix: poses become server-side entities with UUID primary keys. The mobile app fetches them once, maps slug → UUID, and sends the UUID as `ref_id`. The `activityRefId` column stays `uuid` — no type change, no relaxation of the constraint.

---

## What We Need From You

### 1. New table: `meditation_poses`

```sql
CREATE TABLE meditation_poses (
  id            uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  slug          varchar     NOT NULL UNIQUE,
  display_order smallint    NOT NULL
);
```

No `user_id` — poses are global, not user-owned. No soft delete, no `updated_at`. This table is static reference data; rows are added only via migration.

Seed the table in the same migration that creates it, with these exact six rows (UUIDs generated by the migration — no need to fix them in advance):

| slug        | display_order |
|-------------|---------------|
| easy        | 1             |
| lotus       | 2             |
| half_lotus  | 3             |
| seiza       | 4             |
| chair       | 5             |
| savasana    | 6             |

No admin endpoint, no CRUD. If a new pose is added in the future, a developer writes a migration. This is intentional — poses are curated content, not user content, and the strictness of migration-based additions is a feature, not a limitation.

### 2. REST endpoint: `GET /meditation/poses`

Authentication: required (standard JWT Bearer, same as all other authenticated endpoints).

**Response — 200 OK:**

```json
[
  { "id": "<uuid>", "slug": "easy",       "displayOrder": 1 },
  { "id": "<uuid>", "slug": "lotus",      "displayOrder": 2 },
  { "id": "<uuid>", "slug": "half_lotus", "displayOrder": 3 },
  { "id": "<uuid>", "slug": "seiza",      "displayOrder": 4 },
  { "id": "<uuid>", "slug": "chair",      "displayOrder": 5 },
  { "id": "<uuid>", "slug": "savasana",   "displayOrder": 6 }
]
```

UUIDs are generated by `gen_random_uuid()` in the seed migration — they are not pre-agreed. Mobile always fetches them at runtime; nothing on the mobile side hard-codes a pose UUID.

Always sorted by `display_order ASC`. No pagination — the list is bounded and small. No filtering parameters. No `name`/`title` field — display names are owned by the mobile app's localisation layer.

The endpoint does not need its own NestJS module. It can live inside whatever existing module is most natural (`MeditationModule`, `RealtimeModule`, or a new lightweight `MeditationPosesModule` — your call).

### 3. No changes to `module_sessions`

The `activityRefId uuid` column already has the right type. Once the mobile app starts sending a real UUID (pose ID from this table), inserts will succeed. Nothing else in `module_sessions` needs to change.

---

## What Mobile Will Do After You Ship

1. On meditation module open, mobile calls `GET /meditation/poses`.
2. The response is cached in memory for the duration of the app session (no local DB persistence needed — the list is short and stable).
3. When the user selects a pose and starts a session, mobile maps `slug → id` from the cached list and sends `ActivityStartCmd { activity_type: MEDITATION, ref_id: <pose UUID> }`.
4. `module_sessions.activityRefId` will contain a valid `meditation_poses.id` UUID for every meditation row.

The mobile app keeps the `kMeditationPoses` hardcoded list as a display fallback (for localised names and ordering while the fetch is in flight), but the UUID used for recording always comes from the server response.

## Integration Contract

| Direction | Field | Type | Value |
|-----------|-------|------|-------|
| Mobile → API (gRPC) | `ActivityStartCmd.ref_id` | string (UUID format) | `meditation_poses.id` |
| API → DB | `module_sessions.activityRefId` | uuid | same UUID |
| API → Mobile (REST) | `GET /meditation/poses[].id` | UUID string | `meditation_poses.id` |
| API → Mobile (REST) | `GET /meditation/poses[].slug` | string | `'easy'`, `'lotus'`, … |

## Relationship to Note 23 (Meditation Notes)

Note 23 stores `pose_id` as plain `text` in the `meditation_notes` table (denormalised, for resilience against session deletion). That design is intentional and does not need to change — the notes feature stores the slug for display purposes, not for FK integrity. The `meditation_notes.pose_id` column stays `text`.

The `module_sessions.activityRefId` column, by contrast, must stay `uuid` — it is the ML/analytics join key between a session and its pose. Different tables, different requirements.
