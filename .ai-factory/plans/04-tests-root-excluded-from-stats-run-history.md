# Plan: Tests — root excluded from stats + run history

## Context
Write silent-bug-first TDD tests that guard a `root` session from inflating `user_stats` (streak/duration/totalSessions) and from surfacing in `listRuns`, while proving the over-guard risk is covered: the bio flush riding the same shared `ABANDONED` event must still fire for a root. Target cases are expected RED until feature spec `07-exclude-root-from-stats`; characterization cases must stay GREEN.

## Settings
- Testing: yes (this milestone's deliverable is test code)
- Logging: minimal
- Docs: no

## Constraints (from spec note 18 — read before writing)
- **L1 — observe the right outcome at the guard's own layer.** Spec 07 places **both** guards *inside* code the unit test cannot see through a forwarding spy: the stats guard is an early return at the **top of `StatsService.finalise`** (`07-exclude-root-from-stats.md:18-22` — *not* in `StatsWorker`), and the run-history guard is a SQL `.andWhere` (`07-exclude-root-from-stats.md:23-26`). Consequences for assertions:
  - **Stats exclusion (Task 1):** the observable is the **`user_stats` write being skipped**, observable only by driving the **real `StatsService.finalise`** and asserting `repo.manager.transaction` is not called (mirroring the existing sub-threshold case at `stats.service.spec.ts:98-106`). A `StatsWorker.finalise` spy is the **wrong layer** — the worker calls `finalise` unconditionally for every event type (`stats.worker.ts:32-49`), so a "finalise not called for root" assertion is permanently RED regardless of spec 07. Do **not** put the stats target in the worker spec.
  - **Run-history exclusion (Task 3):** a mocked QueryBuilder cannot reflect a SQL `andWhere` in its output, so that case asserts the **builder contract** (an `andWhere` carrying an `activityType` filter), not the `items` outcome. See Task 3 for why.
  - In all cases, never assert the internal predicate expression itself (e.g. `event.activityType === ActivityType.ROOT`) — assert the downstream effect (no transaction / `andWhere` present), which spec 07 is free to reach however it branches.
- **L2 compile-now:** `ActivityType.ROOT` does **not** exist in the enum yet (`src/realtime/enums/activity-type.enum.ts` has only `BREATH`, `MEDITATION`). In every fixture set `activityType: 'root' as any` — mirror `multi-session-lifecycle.spec.ts`. `SessionEvent.startedAt`/`endedAt` are real `Date` objects (`stats.service.ts:9-14`) — always supply real Dates so `.getTime()` works.
- **L3 label by spec name — targets only:** the two genuine target cases (Task 1 stats-skip, Task 3 builder-contract) must be labelled `RED until spec 07-exclude-root-from-stats` in the `it(...)` description — never a phase number. The invariants (Task 2 bio-flush, Task 1/Task 4 characterizations) are **not** targets — do **not** stamp "RED until" onto them (doing so re-creates the review-1 #2 contradiction).
- **L4 escalation valve:** the "practice still writes stats / still flushes / still min-duration-filters" cases are characterization invariants. A RED there after spec 07 lands means the guard caught the wrong type → genuine Class-B bug → escalate to spec 07, do not patch the test.
- **Do not implement the feature here.** Target tests are *expected* to fail now (root still writes `user_stats`, root still surfaces in `listRuns` because no `andWhere` excludes it). Red-for-the-right-reason is the done state. Do not skip/suppress them.

## Tasks

### Phase 1: Stats service — root skip (real `finalise`, not the worker)

- [x] **Task 1: Add the root-skip target to `StatsService.finalise`**
  Files: `src/stats/stats.service.spec.ts`
  **Why the service, not the worker:** spec 07 guards at the top of `StatsService.finalise` (`07-exclude-root-from-stats.md:18-22`), *not* in `StatsWorker`. The worker forwards every event type to `finalise` unconditionally (`stats.worker.ts:32-49`), so a worker-spy "finalise not called for root" assertion is permanently RED and never observes spec 07's guard. Drive the **real** service instead — the same layer the existing min-duration skip is tested at (`stats.service.spec.ts:98-106`).

  Extend the existing spec (do not rewrite it). Reuse its `makeService()` / `makeEvent(start, end, overrides)` helpers (`stats.service.spec.ts:9-22, 82-96`). Add a `describe('finalise — root excluded', ...)` block:
  - **Target → RED until spec 07-exclude-root-from-stats:** `should NOT write user_stats for a root session` — build a root event with `makeEvent(start, end, { activityType: 'root' as any })` where `end - start` is **above** `WS_MIN_SESSION_DURATION_S` (e.g. 20_000 ms, so the min-duration gate does **not** pre-empt the assertion and mask whether the root guard fired), call `await svc.finalise(event)`, and assert `expect(repo.manager.transaction).not.toHaveBeenCalled()` (same skip-observable as the sub-threshold case at `:104`). Today no root guard exists → `finalise` runs the transaction → RED for the right reason. After spec 07 adds the `ActivityType.ROOT` early return → GREEN.
  - **Characterization counterpart — tag, don't duplicate:** the "a non-root session **does** write `user_stats`" invariant is already covered by the first-session / streak cases at `stats.service.spec.ts:108-257` (they assert `mgr.save`/`transaction` ran for a `breath` event above threshold). Do **not** add a new "breath still writes" case — add a one-line comment in the new block pointing at those existing cases as the non-root write invariant. A RED there after spec 07 = guard caught the wrong type → escalate.

  Leave `src/stats/stats.worker.spec.ts` untouched — it has no spec-07 guard to exercise.

### Phase 3: Run history exclusion

- [x] **Task 3: Add `listRuns` root-exclusion cases (builder-contract assertion)**
  Files: `src/sessions/sessions.service.spec.ts`
  The existing spec only covers `deleteRun`; add a new `describe('SessionsService.listRuns', ...)` block. `SessionsService` is constructed with three repos (`new SessionsService(moduleSessionRepo, bioSampleRepo, streamSampleRepo)`, `sessions.service.ts:50-57`). `listRuns` builds a query via `moduleSessionRepo.createQueryBuilder('ms')` and chains `leftJoin → addSelect → addSelect → where → andWhere → orderBy`, then `getCount()` and `.take().skip().getRawAndEntities()` (`sessions.service.ts:78-97`). Build a chainable QB mock where **every builder method (`leftJoin`/`addSelect`/`where`/`andWhere`/`orderBy`/`take`/`skip`) returns the same QB object** so the calls can be inspected afterwards, `getCount` resolves a number, and `getRawAndEntities` resolves `{ entities, raw }`. Each `ModuleSession` entity needs `id`, `userId`, `startedAt: Date`, `endedAt: Date`, `activityType`; `raw[i]` needs `bs_description`/`bs_complexity` (use `null`).

  **Why outcome-only is untestable here (read before writing).** The run-history exclusion is implemented in spec 07 as a **SQL-level** `.andWhere('ms.activityType != :root', …)` (`07-exclude-root-from-stats.md`). With a fully mocked QB, `.andWhere(...)` is an inert stub: it cannot change what `getRawAndEntities` returns, and `listRuns` maps **every** returned entity into `items` with no JS-side filter (`sessions.service.ts:99-113`). So an outcome-only assertion (seed a root row, expect it absent from `items`) is RED now **and stays RED after spec 07** — the mock keeps returning the seeded root regardless of the new clause. Worse, an implementer chasing that red would likely add a JS `.filter()` after `getCount()`/`take`/`skip`, inflating `total` and short-paging — a pagination bug the test would be *steering toward*. The `ROADMAP_TESTS.md` "no real DB" rule rules out an e2e test that would exercise the real WHERE. Therefore this one case asserts the **builder contract** instead (the L1 carve-out noted above).

  Cases:
  - **Target → RED until spec 07-exclude-root-from-stats:** `should add an activityType != root filter to the listRuns query` — call `listRuns('user-1')`, then inspect `moduleSessionRepo.createQueryBuilder('ms')`'s returned QB: assert that **at least one `andWhere` call's first argument is a string containing both `activityType` and `!=`** (e.g. `qb.andWhere.mock.calls.some(([sql]) => /activityType/.test(sql) && /!=/.test(sql))`). Keep the matcher loose on the bound value — do **not** assert the param name or `ActivityType.ROOT` (it does not exist yet, L2), only that *some* `andWhere` introduces an `activityType` inequality. Today `listRuns` issues only `where(userId)` + `andWhere('ms.endedAt IS NOT NULL')` (`sessions.service.ts:88-89`), so no such call exists → RED for the right reason. After spec 07 adds the clause → GREEN. This is the milestone's deliberate exception to outcome-only assertion.
  - **Characterization (GREEN now, stay GREEN):** `should still return breath and meditation rows mapped from the query result` — seed `getRawAndEntities` with `BREATH` + `MEDITATION` entities (both with `endedAt` set), assert both appear in `items` with their `id`/`activityType`/`durationSeconds` mapped through (`sessions.service.ts:99-113`). This locks the row-mapping shape and proves spec 07's new clause does not disturb the result mapping. (It does not — and cannot — verify the root is filtered out, because the mock ignores the clause; that verification is the target case above.)
