# Plan: Add port 50051

## Context
Expose gRPC port 50051 in both Docker Compose configurations so the NestJS service is reachable over gRPC from outside the container. Also fix the production Dockerfile which is missing the `proto/` directory required by the gRPC transport at runtime.

## Settings
- Testing: no
- Logging: minimal
- Docs: no

## Tasks

### Phase 1: Environment variables

- [x] **Task 1: Add gRPC port env vars to .env.dev and .env.prod**
  Files: `.env.dev`, `.env.prod`
  Follow the existing pattern used for HTTP (`HOST_API_PORT`/`CONTAINER_API_PORT`). Add two new variables to the `# gRPC` section of each file:
  ```
  HOST_GRPC_PORT=50051
  CONTAINER_GRPC_PORT=50051
  ```
  This keeps port configuration in one place and avoids a mismatch if `GRPC_URL` is ever changed. Note: `GRPC_URL=0.0.0.0:50051` already exists in both files — leave it as-is.

### Phase 2: Docker Compose

- [x] **Task 2: Add gRPC port mapping to docker-compose.dev.yml** (depends on Task 1)
  Files: `docker-compose.dev.yml`
  In the `mind_api_dev` service, add a second entry to `ports` below the existing HTTP mapping:
  ```yaml
  - "${HOST_GRPC_PORT}:${CONTAINER_GRPC_PORT}"
  ```

- [x] **Task 3: Add gRPC port mapping to docker-compose.prod.yml** (depends on Task 1)
  Files: `docker-compose.prod.yml`
  Same change in the `mind_api_prod` service — add the gRPC port mapping using the env vars.

### Phase 3: Dockerfile fixes

- [x] **Task 4: Copy proto/ directory in the production Dockerfile stage**
  Files: `Dockerfile`
  The production stage only copies `dist/`, `node_modules/`, and `package*.json`. The gRPC transport loads raw `.proto` files at runtime via `@grpc/proto-loader` from `proto/`. Without this directory the container crashes on startup. Add after the existing COPY lines in the `production` stage:
  ```dockerfile
  COPY --from=builder --chown=nestjs:nodejs /app/proto ./proto
  ```

- [x] **Task 5: Add EXPOSE 50051 to both Dockerfile stages**
  Files: `Dockerfile`
  Add `EXPOSE 50051` next to the existing `EXPOSE 3000` in both the `production` and `dev` stages. While `EXPOSE` is documentation-only, it's standard practice for discoverability and tooling (`docker inspect`, orchestration tools).
